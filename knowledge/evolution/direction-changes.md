# 项目方向调整记录

> 记录 DavyLinks 经历的重大方向变化：改了什么、为什么。防止未来重复踩坑或误推翻。

## 调整 1: 运行框架 — Hermes Agent 编排 → 纯 Python 管线

**时间**: v1.0 期间 (2026-05)

**原设计**: 全流程由 Hermes Agent cronjob 编排，扫描用 blogwatcher skill、摘要用 delegate_task、推送用 terminal 调用 notify.py——LLM Agent 作为调度中枢。

**调整为**: 独立 Python 脚本管线（`scripts/pipeline.py` 编排六个阶段），Hermes 退化为单纯的定时触发器。

**原因**:
- Agent 编排不可预测：每次运行路径可能不同，失败难以复现和调试
- 成本高：每个阶段都是一次 Agent 推理，token 消耗大且无必要——流程是确定性的，不需要智能调度
- Python 脚本可单测、可 dry-run、可分阶段调试，工程可控性完全不同

**教训**: 确定性流程不该用 LLM Agent 做编排。Agent 适合"决策不确定"的环节，不适合"流程确定"的管道。Skill 文件（`skills/davylinks-pipeline.md`）保留，但只作为触发入口说明。

## 调整 2: 阶段拆分 — 5 阶段 → 6 阶段（新增飞书表格）

**时间**: v1.0 → v2.0

**原设计**: 5 阶段，飞书只有群消息推送一个出口。

**调整为**: 新增 Phase 3.5 飞书多维表格写入（`feishu_bitable.py`），形成双出口：
- 多维表格 = 全量记录（可回溯）
- 群消息 = TOP 5 精华（日常阅读）
- Obsidian = TOP 5 沉淀（长期知识）

**原因**: 只有群消息一个出口时，历史信息转瞬即逝；Obsidian 又只存 TOP 5。"想找上周看过的某篇文章"这个高频需求没有出口。多维表格承担完整档案职能后，[ADR-005](../decisions/005-top5-only-obsidian.md) 的"仅 TOP 5 入 Obsidian"才成立。

## 调整 3: 配置管理 — 各脚本自治 → 统一 config_loader

**时间**: v2.0 (2026-06)

**原设计**: 每个脚本自己实现配置加载，`_parse_yaml_simple` 被复制了 3 份。

**调整为**: `scripts/config_loader.py` 单点实现全部配置加载（secrets 合并、优先级、各类 getter），其余模块只调用。

**原因**: 三份复制实现已经出现行为漂移风险；配置优先级（环境变量 > config/secrets.yaml > ~/.davylinks/secrets.yaml）必须全局一致才可推理。

**教训**: 复制粘贴配置逻辑是最典型的 DRY 违规——它不会立即坏，但会在你最意想不到的时刻行为不一致。

## 调整 4: 质量路线 — 功能优先 → 质量/安全优先

**时间**: v1.0 → v2.0

v1.0 的主题是"跑通"：三天内从零到每日推送。代价是积累了硬编码凭证、SQL 注入、数据突变等 14 个已知问题。

v2.0 主题转为系统性 code review：3 严重 + 4 高 + 7 中问题全部修复，并建立 19 个测试用例的回归防线（含 7 个不可变性测试）。

**教训**: MVP 跑通后应立即安排一次专门的清理迭代，而不是继续堆功能。债务拖得越久，修复成本越高（v2.0 的 14 项修复花了整整一轮）。
