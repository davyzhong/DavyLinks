## 阶段总结

v1.0 是 DavyLinks 的首个可用版本。这一阶段把最初 `scan_articles.js` 单文件 300 行的原型，重构为按阶段职责分离的 Python 管线，并补齐了原设计遗漏的关键基础设施：去重、日志、配置管理、错误处理。

来源文档：`OPTIMIZATION_COMPLETE.md`（v1.0 部分）。

## 4 个严重问题修复

### 1. 飞书凭证硬编码

- **问题**：飞书 app_id / app_secret 直接写在代码里，有泄露风险且无法多环境切换。
- **修复**：改为 `load_feishu_config()`，支持环境变量 + `config/secrets.yaml` 双层配置。
- **教训**：密钥、token 永远不进代码、不进 commit。项目起步就要有 `secrets.example.yaml` 模板和 `.gitignore`。

### 2. LLM API 格式 bug

- **问题**：不同 LLM provider 的 API 格式不同，混用导致调用失败。
- **修复**：定义 `ANTHROPIC_PROVIDERS = {"kimi", "zhipu"}`——Kimi/Zhipu 用 Anthropic 格式，Qwen/MiniMax 用 OpenAI 格式。
- **教训**：多 provider  fallback 架构下，API 格式差异必须在统一入口处显式声明，不能散落在各调用点。

### 3. timedelta 导入缺失

- **问题**：`timedelta` 在函数内使用但未在模块级导入，运行时报错。
- **修复**：移到模块级导入。
- **教训**：这类错误本该被最基本的编译检查发现——v2.0 因此引入了 `check.sh`（编译 + 测试）。

### 4. mark_processed 无法更新摘要

- **问题**：使用普通 INSERT，URL 主键冲突时无法更新已有记录的摘要字段。
- **修复**：改用 `INSERT OR REPLACE`。
- **教训**：去重表的写入语义要想清楚是「仅插入」还是「upsert」；摘要补写场景需要后者。v2.0 进一步用 `executemany` 优化了批量写入性能。

## 性能对比：话题聚类 O(n²) → O(n)

### 优化思路

原实现是两两比较所有文章的 O(n²) 聚类。优化后采用**倒排索引**：预计算每篇文章的实体和二元组（bigram），以实体为键建索引，只对共享实体的文章对做比较。

### 效果

| 文章数 | 优化前 (O(n²)) | 优化后 (O(n)) | 提升 |
|--------|----------------|---------------|------|
| 20 | ~50ms | 0.8ms | 62x |
| 50 | ~300ms | 0.2ms | 1500x |
| 100 | ~1200ms | 0.5ms | 2400x |

**比较次数减少**: 80-95%

### 实际运行日志示例

```
预计算 87 篇文章的实体和二元组...
实体索引：34 个实体，覆盖 62 篇文章
候选比较对：127 对 (原始 O(n²)=3741)
实际比较次数：127 (节省 96.6%)
```

## 经验沉淀

1. **基础设施不能事后补**：去重、日志、配置管理是管线类项目的地基，原型阶段就该有雏形。
2. **算法优化先量化**：聚类优化有明确的 before/after 数据（2400x），比模糊的「性能更好」有说服力。
3. **设计决策要显式记录**：保留的问题（subprocess 开销、run_log 覆盖）都标注了「设计决策」，避免后人误判为疏漏。
4. **单文件拆分的收益**：职责分离后每个脚本可独立运行调试，为 v2.0 的可测试性改造打下基础。
