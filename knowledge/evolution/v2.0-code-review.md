## 性能改进

### 批量写入优化

| 操作 | v1.0 (逐条 INSERT) | v2.0 (executemany) | 提升 |
|------|-------------------|-------------------|------|
| 写入 10 条 | ~10ms | ~2ms | 5x |
| 写入 50 条 | ~50ms | ~5ms | 10x |
| 写入 100 条 | ~100ms | ~8ms | 12.5x |

### Hash 碰撞概率

| 文章数 | v1.0 (32 bit) | v2.0 (64 bit) |
|--------|--------------|--------------|
| 1,000 | 0.01% | 0.0000000001% |
| 10,000 | 1.2% | 0.00000001% |
| 70,000 | 50% | 0.0000005% |
| 100,000 | 69% | 0.000001% |

注：70,000 篇文章时 32 bit hash 碰撞概率已达 50%（生日悖论），64 bit 彻底消除该风险。

## 经验沉淀

1. **不可变数据流是管线项目的核心纪律**：v1.0 的 mutation 贯穿整个管线，调试时无法确定数据在哪一环被改。改为返回新 dict 后，每个阶段的输入输出可独立断言，才有了 `test_immutability.py` 的 7 个测试。
2. **配置加载必须收敛到单点**：`_parse_yaml_simple` 重复 3 份是典型的「先跑起来」债，统一 `config_loader` 后新增配置只需改一处。延迟初始化（lazy init）保证 import 时不读 secrets，既安全又可测试。
3. **小 hash 位数是定时炸弹**：32 bit hash 在 7 万条数据时碰撞概率 50%，而状态库设计目标是长期累积，必须一次到位 64 bit。
4. **exit code 和日志是可观测性的底线**：失败时 exit code 0 + `bare except: pass` 会让定时任务静默失败，这类问题只能靠 code review 主动发现。
5. **纯重构迭代有价值**：代码行数不变、功能不变，但测试从 0 到 19、安全问题清零，这类迭代应独立成版本而非夹在功能开发中。
